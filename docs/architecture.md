# Как устроен kireevonline.ru

## Где что живёт

```
Mac (~/Claude Code/kireevonline/)          GitHub (приватный)           Сервер Sprinthost
├── gallery/   код, git ───────────────▶  код и история                ├── domains/kireevonline.ru/gallery/   код (git) + db.sqlite3
├── backups/   копии базы, фото, архивы                                   ├── domains/kireevonline.ru/public_html/
├── .venv/     Python для запуска на Mac                                  │     media/  фото     static/  стили, скрипты
├── notes/     заметки к альбомам (личное)                                │     site.wsgi  запуск (секреты — только здесь)
└── _архив/    старые версии                                              ├── deploy-backups/   снимки базы перед выкладками (10)
        │                                                                 └── ro-gate.py        шлюз только для чтения
        └── выкладка: deploy/deploy.py по SSH-ключу владельца ───────────▶
```

Сервер в GitHub не ходит и ключей от него не хранит: код на сервер приносит скрипт выкладки с Mac.
Фото и база на GitHub не попадают — их хранят бэкапы на Mac и архивы для облака.

Хостинг: Apache + mod_wsgi, Python 3.13 (свой venv), git 1.8.3, квота 2 ГБ (занято ~1,6 ГБ — тяжёлое на
сервере не хранить). Перезапуск сайта — обновить время файла `site.wsgi`; хостинг подхватывает его
то за секунды, то за минуты.

## Данные

| Модель | Что это | Важное |
|---|---|---|
| `Section` | раздел: Репортаж, Путешествия, Прогулки, Портреты | порядок, «скрыт», обложка, адрес (slug) не меняется при переименовании |
| `Album` | альбом внутри раздела | порядок, «скрыт», место, месяц, «Коротко», записки, «Снято на», обложка |
| `Photo` | фото | файл (до 1920 px, JPEG 85) и превью (~1080 px), раздел, альбом, порядок, корзина (`is_deleted`) |

Удаление — сначала в корзину: файлы остаются, фото можно вернуть. Стереть навсегда — из корзины; файлы
удаляются только после того, как удаление записано в базу (если запись сорвалась — файлы на месте).
При удалении альбома его фото уходят в корзину. Уборка лишних файлов на «Диске» не трогает файлы моложе суток.

**Раздел фото всегда равен разделу его альбома** — это делает сама модель при сохранении, на любом пути
(загрузка, перенос, панель Django); альбом переезжает в другой раздел вместе с фото.

**«Скрыт» — это черновик, а не секрет.** Скрытые раздел или альбом не видны посетителям на страницах, в меню,
на главной, в «Барабане», в обложках и превью ссылок (одно правило — `Photo.objects.visible()`), страница по прямой
ссылке — 404. Но сами файлы фото лежат в общей папке `media/`, и тот, кто знает точный адрес файла, его откроет.
Для личной галереи этого достаточно; если понадобятся действительно закрытые фото — нужна выдача файлов с
проверкой прав (решение — в `docs/decisions.md`).

Миграции (`photos/migrations/`) — обратимые по структуре: откат выкладки возвращает схему базы обратными
миграциями, данные владельца (фото, тексты) при этом сохраняются. Исключение — старые шаги с наполнением
(0009, 0010–0013): их обратный ход возвращает тексты и файлы «как было до шага», поэтому откатываться за
них нельзя без снимка базы. Файлы шага 0009 лежат рядом с ним в `files_0009/`.

## Код

```
config/      settings.py (безопасно по умолчанию: без DJANGO_DEBUG сайт «боевой»), urls.py, security.py, version.py
photos/
  models.py          Section, Album, Photo
  views/pages.py     главная, раздел, альбом, «Барабан», «Обо мне»
  views/panel.py     панель: порядок, скрытие, переименование, создание, тексты, перенос фото, обложка
  views/uploads.py   загрузка частями: проверка, что файл — фото, сжатие, превью
  views/trash.py     корзина          views/disk.py   «Диск»: место, лишние файлы
  views/seo.py       robots.txt, sitemap.xml, security.txt
  urls.py            публичные адреса + старые /photos/… → новые
  panel_urls.py      /admin/…
  action_log.py      журнал действий админа (стандартный журнал Django)
  templates/photos/  страницы; panel/ — страницы панели
static/      css/site.css, js/site.js (просмотр фото, сетка, выбор), js/menu.js (шапка), fonts/ (Oswald, OFL)
deploy/      deploy, rollback, status, backup, archive, verify_backup, setup_readonly, server.py (общее), readonly_gateway.py
```

Загрузка (`views/uploads.py`, `media.py`): браузер шлёт фото частями по 400 КБ (сотни фото за раз переживают
обрывы связи). Сервер:
- запоминает параметры загрузки (альбом, имя, число и размер частей) при первой части и не даёт их менять;
- собирает фото, только когда пришли все части и размер сходится; сборка — ровно один раз: фото хранит номер
  своей загрузки (`Photo.upload_key`, уникален), поэтому повтор после любого обрыва возвращает то же фото,
  а второе база записать не даст; «замок» сборки, брошенный при обрыве, снимается через 5 минут;
- до записи в базу полностью разбирает картинку (только JPEG/PNG/WebP — другие форматы даже не разбираются),
  ограничивает размер (120 Мп), ужимает до 1920 px, стирает данные камеры, делает превью ~1080 px;
  битый или чужой файл — отказ с причиной, в базе и на диске ничего не остаётся; сорвалась запись в базу или
  превью — файлы этой попытки стираются.
Страница загрузки фиксирует раздел и альбом на всю партию; если вход истёк — останавливается и просит войти снова.
Повторное сохранение фото его не пережимает. В запасной панели Django загрузки и замены файлов фото нет.

Сетка альбома сразу просит у сервера только первые 40 превью, остальные — по мере прокрутки
(иначе хостинг отказывает в части запросов). «Барабан» собирает каждую ленту из своих картинок.

## Защита

- https обязателен, HSTS на год, cookie входа только по https, запрет встраивать сайт в чужие страницы.
- **Content-Security-Policy:** браузер выполняет только скрипты самого сайта (файлы и встроенные с одноразовым
  nonce) и ничего не грузит с чужих серверов. Обработчики вида `onclick="…"` в шаблонах запрещены (тест).
- **Вход:** одна страница `/admin/login/` для своей панели и панели Django. После 5 неверных паролей с одного
  адреса за 15 минут или 30 за час на весь сайт форма закрывается на паузу и пароль не проверяет. Счётчики —
  файлы с блокировкой во временной папке: работают для всех процессов сайта, окно не сокращается. Общий лимит
  может на время закрыть вход и владельцу — принято сознательно. Адрес посетителя берётся из `X-Real-IP`,
  который ставит прокси хостинга (что хостинг не пропускает подделанный — не проверено).
- **Журнал действий** админа — «Панель Django» → «Журнал действий», только для чтения.
- Загрузка принимает только фото, и только через свою панель. `/.well-known/security.txt` — куда сообщить об уязвимости.
- Без настроек окружения сайт запускается безопасно: отладка выключена, ключ случайный.

## Выкладка и откат

`deploy/deploy.py` (запускает только владелец):
1. Автотесты на выкладываемой версии (`origin/main`) во временной копии кода — не прошли, выкладки нет.
2. Проверка сервера через SSH: версия, нет ли ручных правок. Список изменений, предупреждение о миграциях и библиотеках.
3. «да» владельца.
4. Снимок базы и списка библиотек на сервере + копия базы на Mac. Меняются библиотеки, а их список снять
   не удалось — выкладки нет. На сервере ставится отметка «выкладка начата» (`pending-deploy.json`).
5. Код на сервер (`git push` в ветку `deploy-incoming`), на сервере — `git reset` на эту версию, при необходимости
   `pip install`, `migrate`, `collectstatic` (и при новых библиотеках — их стили тоже), перезапуск. На сервер
   для этого временно передаётся программа-помощник (`REMOTE_HELPER` в `deploy/server.py`), постоянно ничего не ставится.
6. Проверка живого сайта: главная, альбом, robots.txt, sitemap.xml — и что каждая отвечает новой версией
   (заголовок `X-Site-Version`); до 6 минут, раз в минуту «пинок» перезапуска.
7. Проверка не прошла — сам возвращает прежнюю версию (и базу из снимка «до», если менялась структура).
8. Запись в журнал на сервере и на Mac; запись «готово» снимает отметку. Не записалось — скрипт об этом говорит.

Если выкладку прервали (закрыли окно, оборвалась связь), отметка остаётся: следующий запуск видит, что выкладка
не завершена, и доделывает её от последней завершённой версии; для возврата берёт снимки базы и библиотек,
сделанные до прерванной.

`deploy/rollback.py` — к версии до последней выкладки или `--to <версия>`. Структура базы возвращается обратными
миграциями; если они сорвались посередине — база возвращается из снимка, сделанного прямо перед откатом.
`--restore-db` (база из снимка) — только вместе с той версией кода, для которой снимок сделан. Откат через шаги
базы с текстами (0009–0013) запрещён: их обратный ход стёр бы тексты, написанные позже.
Откат тоже ставит отметку: если его прервали, следующий запуск выкладки или отката сначала возвращает сайт к
состоянию до него (код, база и библиотеки — из снимков перед откатом) и просит запустить команду ещё раз.
Одновременные выкладка и откат не блокируются — их запускает один человек по очереди.

## Доступ AI-помощника

Разработка ведётся с AI-помощником (Claude Code) — его инструкции в `CLAUDE.md` и `.claude/skills/`.
На сайте следов AI нет: сайт ни к каким AI-сервисам не обращается.

- Сервер помощник может только читать: отдельный ключ, по которому сервер запускает лишь `ro-gate.py`
  (`deploy/readonly_gateway.py`), а тот умеет только отдать состояние, базу, фото и журнал.
- Блокировка на Mac (`~/.claude/hooks/kireevonline-guard.sh`, вне проекта — чтобы её нельзя было ослабить
  правкой кода) не даёт помощнику запускать выкладку, откат, настройку сервера и ходить на сервер напрямую.
  Проверка блокировки — `deploy/tests/test_guard.py`.
- Это защита от случайностей, а не от человека с доступом к Mac владельца.

## Проверки

| Уровень | Что | Где |
|---|---|---|
| перед каждой версией | стиль (ruff) + тесты сайта + проверка блокировки | `.githooks/pre-commit` |
| на GitHub | то же + выкладка, откат, автовозврат на копии сервера | `.github/workflows/tests.yml` |
| перед выкладкой | всё выше + браузер + обратимость миграций на копии базы сайта | скил `release`, `browser_checks/` |

Проверки в браузере в автозапуск на GitHub не входят (нужна копия сайта с фото); все сообщают «прошло / не прошло»,
все разом — `node browser_checks/run_all.mjs`. Перекрёстная проверка кода моделями GPT и Claude 09.10.2026 —
`docs/reviews/2026-10-09-cross-review-1.md` и `…-cross-review-2.md`.

## Бэкапы

- Перед каждой выкладкой — снимок базы на сервере (последние 10) и копия на Mac.
- `deploy/backup.py` — база и новые фото на Mac (`../backups/`); фото, удалённые на сервере, на Mac остаются.
  Совпадение фото сверяется по размеру файла (сверка содержимого — в бэклоге).
- Порядок (решение владельца): снимок перед каждой выкладкой, полный архив для облака раз в месяц и по команде;
  ежедневный бэкап не нужен — на сайт загружается редко.
- `deploy/archive.py` — архив «под ключ» для облака: код той версии, что работает на сервере (и вся история),
  база без учётных записей, все фото сервера и все файлы, на которые ссылается эта копия базы, шаблоны настроек
  хостинга, `ВОССТАНОВЛЕНИЕ.md`, контрольные суммы. Перед упаковкой — проверка, что копия базы подходит к коду
  (тот же последний шаг базы), иначе — сначала свежая копия. Уже собранный архив проверяется: всё, на что
  ссылается база, в нём есть. Распаковка и проверка — скил `backup`; восстановление сайта с нуля из архива проверено 29.09.2026 на Mac (на отдельном сервере — не проверялось).
